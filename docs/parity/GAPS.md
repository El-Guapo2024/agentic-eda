# agentic-eda vs KiCad — Top 30 Gaps

Ranked by user-visible impact (does it block a whole workflow, or shave a corner off one you can already do). Engine gaps are grounded in this project's own source (`crates/drc/src/item.rs`'s `ErrorType`, `crates/kicad/src/erc.rs`'s check registry) against KiCad's real catalogs (`pcbnew/drc/drc_item.cpp`, `eeschema/erc/erc_item.cpp`), corroborated by the live numbers in `docs/parity/REPORT.md` (precision/recall per type, match rates, import success, and two findings the live run surfaced that source-reading alone would have missed — see #2 and #3). UI gaps are grounded in a full read of `web/studio/src`'s action registry, dialogs, and canvas interaction code against `pcbnew/tools/*`, `eeschema/tools/*`, and `common/tool|view/*`.

Catalog-coverage headline, independent of any one board sample: KiCad's `DRC_ITEM::allItemTypes` names **67** distinct DRC check types; `eda_drc::ErrorType` defines **23** of them (plus `eda_connectivity`'s `unconnected_items` = 24/67, **36%**). KiCad's `ERC_ITEM::allItemTypes` names **51** distinct ERC check types; `eda_kicad::check_erc`'s registry covers **12** of them (`pin_to_pin` alone stands in for both `pinTableWarning`/`pinTableError`) — **24%**. Both counts are structural (does a check exist at all); REPORT.md's measured precision/recall is the complementary "does an implemented check actually agree with KiCad" number, and it's much worse than the catalog-coverage number would suggest (see #3).

1. **Area**: eeschema — core schematic editing. **Symptom**: the schematic editor is a read-only viewer: no way to place a symbol, draw a wire, add a label, or move anything. Every `eeschema.*` action (240 cataloged) is unwired; `useActionRunner.ts` registers zero of them. Measured UI parity: **~5%**. **Port from**: `eeschema/tools/sch_drawing_tools.cpp` (`PlaceSymbol`), `sch_line_wire_bus_tool.cpp` (`doDrawSegments`/`startSegments`/`finishSegments`), `sch_edit_tool.cpp`, `sch_move_tool.cpp`. **Size**: XL (root gap — the items below decompose it for actual sequencing).

2. **Area**: DRC — the engine hangs on anything but a tiny board. **Symptom**: discovered live by this harness, not by reading source: `eda_drc::run` timed out (60s watchdog) on 2 of the 4 `examples/ladder/*.yaml` rungs every run (`l3_motor_hub`, 58 parts; `l4_control_hub`, 100 parts) and intermittently on a third (`l2_sensor_hub`, 35 parts — finished in one run, timed out in another, consistent with a severe super-linear cost curve sitting right at the cap rather than a hard infinite loop). `l1_usb_mcu` (17 parts) finishes in ~1-2s every time. No `kicad-cli` child process was running during the original 35-minute hang the orchestrator caught (`sample`-able CPU at ~95%), so the cost is entirely inside our own providers, not the oracle. **This means the DRC engine is effectively unusable on any board past toy size today** — a correctness bug in already-"ported" work, not an acknowledged gap. Not investigated further per this task's scope (measure, don't fix) beyond this localization; the part-count correlation points at one of the pairwise-geometry providers (`copper_clearance.rs`, `courtyard.rs`, `silk_mask.rs`, or `text_dims.rs` — likely an O(n²)-or-worse all-pairs scan with no spatial index) as the most probable location, but this is a hypothesis, not a confirmed diagnosis. **Port from**/**investigate**: profile `eda_drc::run` (`crates/drc/src/lib.rs`) on `examples/ladder/l2_sensor_hub.yaml` at seed 0 first — it's the smallest board that reproduces it. **Size**: M to localize with a profiler, unknown to fix until localized.

**Update (follow-up session, profiled with `sample` per the instruction above):** the hypothesis above was wrong about *which* code is slow. `eda_drc::run` itself is fast and scales fine: 155ms on l2 (19 violations), 608ms on l3 (21 violations), ~1-5s on l4 depending on system load (464 violations) — comfortably inside a 10s budget at every rung, confirmed both by wall-clock timing around just that call and by a `sample` CPU profile (100% of samples landed in `eda_freeroute`'s autorouter -- room/door/maze/cellgrid/searchtree code -- zero in `eda_drc` or its `kimath` geometry). The actual 60s+ wall time this gap measured is almost entirely `place`+`route` *before* DRC ever runs: l3's own breakdown is schematic=8ms, place=20.9s, **route=93.5s**; l4's is place=75.6s, **route=1850.9s** (the latter run was also competing with heavy concurrent CPU load from other agents on the same machine, so treat the absolute number loosely, but the *order of magnitude* and the fact that it dwarfs `place` and `eda_drc::run` by 1-2 orders of magnitude is real and reproducible). So: `crates/drc` was not the super-linear component; `crates/freeroute`'s autorouter is, and that's a separate, much larger investigation (out of scope for the DRC port this gap was written for). `crates/drc/src/providers/copper_clearance.rs` was still given a real `DRC_RTREE`-equivalent spatial index (`crates/drc/src/rtree.rs`, a uniform-grid bbox index bounded by the run's worst-case clearance, matching `drc_test_provider_copper_clearance.cpp`'s actual structure) for its track-vs-track/track-vs-pad/track-vs-via loops, since that was still a real (if not yet board-breaking at these sizes) all-pairs scan and the task asked for KiCad's real structure rather than a size-specific patch; `crates/drc/tests/perf_profile.rs::l4_drc_perf_budget` now guards `eda_drc::run` specifically at a 10s budget in release.

**Second update (same follow-up session, confirmed under quiet load):** re-ran the full parity harness later in a quiet window (`uptime` load average 12-100, down from the earlier 16-418) specifically to get a clean measurement, and `l4_control_hub`'s re-route in `parity_drc.rs`'s `zone_fill_impact` step *still* took 30+ minutes end to end even then. That rules out shared-machine contention as the main cause of the earlier 1850s figure: `crates/freeroute`'s autorouter is genuinely, inherently slow on this board's net/part count, not just unlucky about CPU contention. `zone_fill_impact` (an informational "zone fill impact" sidebar in REPORT.md, now largely superseded by the real zone filler landing upstream) is gated behind `PARITY_ZONE_IMPACT=1` (off by default) in `parity_drc.rs` as of this update, specifically so a plain harness run doesn't pay this cost just to populate one sidebar table. Fixing `crates/freeroute` itself is a separate, much larger follow-up -- out of scope for this DRC-port task.

3. **Area**: DRC — precision on real boards is very low, and at least one check looks outright broken. **Symptom**: measured over 56 boards (17 synthetic + 2 `work/` + 37 real KiCad QA boards — 2 ladder rungs excluded by #2's timeout): **6.3% precision, 14.1% recall** against kicad-cli, after already excluding this project's own non-KiCad placement-quality checks. The clearest single culprit: `tracks_crossing` — KiCad reports **0** across every one of those 56 boards; `eda_drc` reports **1567**, a 100% false-positive rate for that check specifically, on real routed copper. Two more patterns worth naming: `hole_clearance` has zero matched instances despite 378 KiCad / 831 ours (not just under/over-counting — the *positions* disagree every time, suggesting a scope or convention mismatch, not just a threshold difference), and most clearance-family checks (`clearance`, `track_width`, `shorting_items`, `silk_over_copper`) over-fire by roughly 4-10x, consistent with this project checking every net against one global default rule while real boards carry per-net/per-netclass overrides `import_kicad_pcb` doesn't reconstruct (see #10 — likely the same root cause). **Port from**: `pcbnew/drc/drc_test_provider_copper_clearance.cpp`'s crossing/touching-segment predicate (compare against whatever `eda_drc::providers::copper_clearance` or a dedicated crossing check is doing — same-net segments that merely share an endpoint look like the likeliest false-crossing trigger); net-class rule import, see #10. **Size**: M to fix `tracks_crossing` specifically once localized; L for the netclass-import root cause.

**Update (follow-up session):** landed three fixes. (1) `tracks_crossing`'s net-equality check required `.is_some()` before comparing nets, so two same-(unassigned)-net segments were never recognized as same-net; fixed to plain equality. This did *not* move the 1567 figure above, because on inspection all 1567 of those hits come from one board (`issue22475.kicad_pcb`) between segments on genuinely different, assigned nets that real KiCad still doesn't flag, for a reason not yet identified — tracked as a separate follow-up rather than guessed at with an ad-hoc suppression. (2) `hole_clearance`'s pad-vs-pad/pad-vs-via loops were missing the same-net exclusion KiCad's `testPadAgainstItem` applies; adding it cut the raw count 831→633 (-24%, zero regressions across a 40-board sweep), but *matched* is still 0 — that's a separate position/scope mismatch, still open. (3) Net classes are now imported from the sidecar `.kicad_pro`'s `net_settings` (previously only a legacy `.kicad_pcb` s-expression format was parsed, absent from every modern multi-class project sampled), which brought the clearance-family over-fire ratio down from ~4-10x to ~2-7x. Fresh overall measurement: **7.8% precision, 19.2% recall** (up from 6.3%/14.1%), but over only 51 of the original 56 boards — three `examples/ladder/*.yaml` rungs timed out this run (vs. two before), purely from `crates/freeroute` route-step load sensitivity (see #2's updates), not from anything in this gap's fixes. `docs/parity/scores.json`'s `drc_boards_evaluated` floor (56) is intentionally left unmet rather than lowered, pending a decision on whether to raise the harness timeout or otherwise decouple this metric from `crates/freeroute` performance.

4. **Area**: ERC — engine built, zero UI exposure. **Symptom**: `crates/kicad/src/erc.rs` (808 lines) is a real, working ERC engine (measured 34.8% precision / 23.9% recall against kicad-cli once this project's own non-KiCad style checks are excluded from the count) with no way to run it from the app — no action, no route, no results dialog (`grep -rniE "erc" web/studio/src` turns up nothing but incidental substring hits). The task's own named deliverable for this editor is currently 0% reachable from the UI. **Port from**: `eeschema/tools/sch_inspection_tool.cpp::RunERC`/`ShowERCDialog`, `eeschema/dialogs/dialog_erc.cpp` (tree + severity badges + cross-probe) — studio can largely clone the pattern its own `components/DrcDialog.tsx` already proves out for PCB. **Size**: M (the hard part — the engine — is already done; this is a route plus a dialog).

5. **Area**: Zone fill — not ported, both engines and UI. **Symptom**: `export_kicad_pcb` writes a zone's outline only; no fill polygon is ever computed. Measured impact: across KiCad's full 185-board QA corpus, `import_kicad_pcb` skips **5,847 zones** outright (reported in its own `ImportNotes`); on `examples/ladder/l4_control_hub.yaml` specifically, 1 zone survives placement/routing but 0 survive the PCB round trip. `ZoneDialog.tsx` captures net+layer only (no clearance/min-width/priority/hatch/thermal-relief). DRC/connectivity checks that depend on a real fill (`isolated_copper` — 63 missing in the DRC sample; starved-thermal; true zone-to-zone/zone-to-pad clearance) can't be evaluated at all; see REPORT.md's zone-fill-impact section for the concrete before/after on two boards. **Port from**: `pcbnew/zone_filler.cpp` (the fill algorithm itself), `pcbnew/dialogs/panel_zone_properties.cpp` (the dialog), `pcbnew/tools/zone_filler_tool.cpp`. **Size**: L (fill engine) + M (dialog).

6. **Area**: eeschema — no hierarchical sheets in the data model. **Symptom**: a multi-sheet schematic can't even be displayed, let alone navigated; the Hierarchy panel is permanently stuck on one "Root" row by its own code comment. Measured corroboration: of the 33 real QA schematics imported, 9 have sheets this project's importer records as "not descended into"; the same sample's ERC numbers show `unconnected_wire_endpoint` over-firing 318-vs-38 and `wire_dangling` 53-vs-16 against KiCad, consistent with wires that connect through a hierarchical label/sheet pin this project can't follow looking locally dangling to it. **Port from**: `crates/model/src/ir.rs`'s `SchematicSection` needs a `sheets` concept; then `eeschema/tools/sch_navigate_tool.cpp` (back/forward history stack) and `sch_drawing_tools.cpp::DrawSheet`. **Size**: L.

7. **Area**: pcbnew — routing is single-segment-per-click with no push-and-shove, diff pairs, or length tuning. **Update**: largely closed. `crates/pns` now ports push-and-shove routing (walkaround/shove/mark-obstacles, posture, via placement), `D`-drag of an existing segment/corner/via, loop removal, an `OPTIMIZER` (`MERGE_SEGMENTS`+`MERGE_OBTUSE`+`MERGE_COLINEAR`), differential-pair routing (`6`, net-name-suffix pair detection + net-class gap/width), and single-track length tuning (`7`, dialog-driven rather than a live session) -- see `crates/pns/PARITY.md` and `web/studio/PARITY-pcb.md` section 4 for exactly what's faithful vs. scoped down. **Remaining**: `MOUSE_TRAIL_TRACER`/springback, `SMART_PADS`/`FANOUT_CLEANUP`, coupled shove/walkaround for a diff pair, diff-pair length/skew tuning (`8`/`9`), and a router-driven footprint drag -- each tracked individually in `crates/pns/PARITY.md`'s "Known gaps" list. **Port from**: `pcbnew/router/router_tool.cpp` (`PNS::ROUTER`), `pcbnew/tools/pcb_actions.cpp` (`routeDiffPair`/`tuneSingleTrack`/`tuneDiffPair`/`tuneSkew`/`routerShoveMode`/`WalkaroundMode`). **Size**: now S-M for what's left (was L).

8. **Area**: pcbnew — no footprint editor or pad tool. **Symptom**: no way to create or edit a footprint, renumber/push/copy pad properties, or assign a per-footprint 3D model. **Port from**: `pcbnew/tools/footprint_editor_control.cpp`, `pad_tool.cpp`, `pcbnew/dialogs/panel_fp_properties_3d_model.cpp`. **Size**: L.

10. **Area**: pcbnew — no net classes or custom DRC rules, and `import_kicad_pcb` doesn't reconstruct per-net overrides. **Symptom**: `assignNetClass` has no UI; there's no rule language; DRC runs a fixed, non-configurable check set against one global rule set. 11. **Area**: pcbnew — property dialogs are read-only for almost everything. **Symptom**: `FootprintPropertiesDialog.tsx` and the track/via/zone/shape branch of `ItemPropertiesDialog.tsx` are explicitly display-only except track width and text; can't edit a via's diameter/drill, a zone's outline, or any footprint field. Two-layer gap: the backend `Cmd` enum (`api/types.ts`) has no `edit_via`/`edit_zone`/`edit_shape`/`edit_footprint` ops to even call. **Port from**: `pcbnew/dialogs/dialog_footprint_properties.cpp`, `dialog_track_via_properties.cpp`, `dialog_pad_properties.cpp`. **Size**: L.

12. **Area**: pcbnew — move excludes tracks and zones entirely. **Symptom**: `move`/drag works for footprints, vias, shapes, and text, but there is no `Cmd` to move a track or a zone at all. **Port from**: `pcbnew/tools/edit_tool.cpp::Main`/`Drag`. **Size**: M.

13. **Area**: pcbnew — selection is missing modifiers and most item types. **Symptom**: no Ctrl-click XOR or Ctrl+Shift subtract (only plain replace and Shift-add); a drag-box only ever selects footprints — tracks, vias, zones, shapes, and text are never box-selectable even though the box-direction rule itself (left-right = enclosed, right-left = crossing) is correctly ported. **Port from**: `pcbnew/tools/pcb_selection_tool.cpp::SelectRectArea` (selects any `BOARD_ITEM`) and its `m_additive`/`m_subtractive`/`m_exclusive_or` handling. **Size**: M.

14. **Area**: Both editors — no clipboard (cut/copy/paste/duplicate). **Symptom**: nothing can be copied or duplicated anywhere in the app — a basic, constant-use operation on both PCB and schematic. **Port from**: `pcbnew/tools/edit_tool.cpp` (`copyToClipboard`/`cutToClipboard`/`Duplicate`), `eeschema/tools/sch_editor_control.cpp` (`doCopy`/`Paste`). **Size**: M.

15. **Area**: eeschema — cross-tab undo/redo bug. **Symptom**: pressing Ctrl+Z while viewing the Schematic tab silently undoes the last **PCB** edit instead of being a no-op, because `common.Interactive.undo`/`redo` are two of the only actions in `useActionRunner.ts` not wrapped in the `pcbOnly()` guard every sibling action uses. A genuine correctness bug, not just a missing feature. **Port from**: internal fix — `actions/useActionRunner.ts` (add the guard, or scope undo/redo per-tab). **Size**: S.

16. **Area**: pcbnew — hotkey-extraction bug on every platform-conditional default. **Symptom**: Ctrl+Y doesn't redo, Home doesn't zoom-to-fit, F1/F2 zoom in/out don't exist as hotkeys at all (the authors noticed and excluded both rather than fix the extraction), and `drawZone`'s extracted hotkey is a nonsense merge of the Mac and non-Mac bindings. Confirmed systemic across every `#ifdef __WXMAC__` action, not a one-off typo. **Port from**: fix is in `web/studio/tools/extract-actions.js`, reading the `#else` (non-Mac) branch as primary; reference bindings in `common/tool/actions.cpp` and `pcbnew/tools/pcb_actions.cpp`. **Size**: S.

17. **Area**: pcbnew — no click-vs-drag threshold. **Symptom**: a move-drag flags "moved" the instant a grid-snapped delta is non-zero; a sub-pixel jitter between mouse-down and mouse-up on a part can silently nudge it by one grid step. Concrete, reproducible, and cheap to fix. **Port from**: `common/tool/tool_dispatcher.cpp` (`DragDistanceThreshold`=8px, `DragTimeThreshold`=300ms, `include/tool/tool_dispatcher.h`). **Size**: S.

18. **Area**: Both editors — grid snapping is grid-only, missing object/anchor and construction-line snap. **Symptom**: outside the routing/via path (which has a fixed 500 µm anchor snap), moving or drawing anything snaps to the grid only — no snap to a nearby pad/track-end, no snap-to-extension-line at an angle; the schematic grid is additionally a hardcoded constant (`components/schematic/layout.ts`'s `GRID = 1270`) that the shared grid-cycle hotkeys don't even affect. **Port from**: `pcbnew/tools/pcb_grid_helper.cpp::BestSnapAnchor` (25 px + hysteresis), `common/tool/grid_helper.cpp::SnapToConstructionLines`, `eeschema/tools/ee_grid_helper.cpp` (per-item-category grids + live snap-point indicator). **Size**: M.

19. **Area**: DRC — footprint/schematic cross-check (`--schematic-parity`) entirely unimplemented. **Symptom**: `duplicate_footprints`, `missing_footprint`, `extra_footprint`, `footprint_symbol_mismatch`, `footprint_symbol_field_mismatch`, `footprint_filters_mismatch`, `net_conflict` — the whole "does the PCB match the schematic" check group kicad-cli exposes via `pcb drc --schematic-parity` — has no counterpart in `eda_drc`. **Port from**: `pcbnew/drc/drc_test_provider_schematic_parity.cpp` (verify exact filename against the snapshot). **Size**: M.

20. **Area**: ERC — every bus/hierarchical-label check is missing. **Symptom**: `bus_to_bus_conflict`, `bus_to_net_conflict`, `net_not_bus_member`, `bus_definition_conflict`, `multiple_net_names`, `hier_label_mismatch`, `duplicate_sheet_names` — ~7 check types, all blocked on the same root cause as #6 (no bus or sheet concept in the schematic model). **Port from**: `eeschema/erc/erc.cpp`'s bus/hierarchy pass, once `crates/model`'s `SchematicSection` grows sheets and buses. **Size**: M (after #6 lands; coupled, not independent).

21. **Area**: ERC — every multi-unit-symbol check is missing. **Symptom**: `different_unit_net`, `unit_value_mismatch`, `different_unit_footprint`, `missing_unit`, `extra_units`, `missing_input_pin`, `missing_bidi_pin`, `missing_power_pin` — ~8 check types; this project's symbol model has no multi-unit concept to check in the first place. **Port from**: `eeschema/erc/erc.cpp`'s per-unit pass, `crates/kicad/src/symbol_lib.rs` for the data-model side. **Size**: M.

22. **Area**: DRC — signal-integrity / diff-pair checks entirely unimplemented. **Symptom**: `length_out_of_range`, `skew_out_of_range`, `too_many_vias`, `diff_pair_gap_out_of_range`, `diff_pair_uncoupled_length_too_long` — 5 check types with no counterpart; this is the engine-side half of UI gap #7 (no diff-pair/length-tuning tools either, since there's nothing to check against). **Port from**: `pcbnew/drc/drc_test_provider_diff_pair_coupling.cpp`, `drc_test_provider_matched_length.cpp` (verify exact filenames). **Size**: L (needs a diff-pair/netclass-length concept in the model first).

25. **Area**: pcbnew — no align & distribute. **Symptom**: no align-top/bottom/left/right/center or distribute-with-even-gaps for a multi-selection — a basic layout-tidying operation used constantly in real KiCad work. **Port from**: `pcbnew/tools/align_distribute_tool.cpp` (`AlignTop/Bottom/Left/Right/CenterX/CenterY/DistributeItems`). **Size**: S-M.

26. **Area**: pcbnew — no array tool. **Symptom**: no way to stamp a grid or circular array of vias/footprints (common for connector rows, LED matrices, mounting holes). **Port from**: `pcbnew/tools/array_tool.cpp`, `pcbnew/dialogs/dialog_create_array.cpp`. **Size**: M.

**Update (follow-up session): closed for every arrayable kind but footprints.** Ctrl+T now ports both grid (spacing, oblique offset, centring, brick stagger) and circular (centre, count, angle, direction, in-place item rotation) geometry, in both "Duplicate" and "Arrange selection" modes, for tracks/vias/zones/shapes/text; "Arrange selection" also covers a placed part (a pure reposition). See `web/studio/PARITY-pcb.md` section 17 for the full behavior table. **Still open**: arraying *footprints* specifically (the symptom's own headline example) only works via "Arrange selection" on footprints already on the board -- creating new placed copies is not possible, because a `FootprintInstance`'s id is its schematic symbol's id and this model has no "conjure a new placed copy with no symbol behind it" operation (the same restriction `Cmd::Duplicate` already has). Footprint reannotation and the footprint-editor's own pad-numbering half of source's dialog (`ARRAY_AXIS` schemes, `ARRAY_PAD_NUMBER_PROVIDER`) are also not ported -- see that section for why. **Size**: the common grid/circular-of-copper-and-drawing-items case from the original symptom is done; a new-footprint-copies path, if wanted, is its own separate follow-up (L -- it is really "teach the ops layer to place a fresh instance of an existing library footprint with no symbol," a much bigger change than array geometry itself).

27. **Area**: Both editors — no grouping. **Symptom**: no way to group items so they select/move as one unit. **Port from**: `common/tool/group_tool.cpp` (`GroupProperties`/`Ungroup`/`AddToGroup`/`RemoveFromGroup`/`EnterGroup`/`LeaveGroup`); needs a group concept in the board/schematic state first. **Size**: L.

**Update (follow-up session): pcbnew half closed, eeschema half still fully open.** A real `Group` IR type (id/name/member\_ids) now backs Ctrl+G/Ctrl+Shift+G group/ungroup, whole-group selection (clicking any member selects the group instead, unless you're inside it), and enter/leave (double-click a single selected group to enter it, Escape to leave, slotted into the same tiered Escape handler source uses). See `web/studio/PARITY-pcb.md` section 16 for the full behavior table. Still open even for pcbnew: no context-menu entries for any of this (hotkey/double-click/Escape only), `AddToGroup`/`RemoveFromGroup` exist as `Cmd`s with no UI wired to them, no nested groups, no group-aware bulk move/rotate/flip/delete (today "the group" is just its member ids under the hood), and no entered-group overlay rendering. The schematic editor side (`eeschema.*`) is untouched by this update — it remains exactly the gap originally described here, blocked on the same root issue as gap #1 (core schematic editing isn't wired up at all yet). **Size**: now S for what's left on the pcbnew side (context menu entries, add/remove-from-group UI); the eeschema half is still its own L, unstarted.

28. **Area**: pcbnew — no dimensioning or ad-hoc measurement tools. **Symptom**: no aligned/center/radial/orthogonal dimension or leader (a basic fabrication-drawing need), and no on-demand ruler beyond incidental dx/dy/dist in the status bar while mid-move. **Port from**: `pcbnew/tools/drawing_tool.cpp::DrawDimension`, `pcbnew/dialogs/dialog_dimension_properties.cpp`; `ACTIONS::measureTool` (`common/tool/actions.cpp`) + handler in `common/tool/common_tools.cpp`. **Size**: M.
