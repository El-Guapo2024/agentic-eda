## Findings

### F1. Finish Pad Edit (Recombine) takes in only shapes that touch the pad as it was before the merge. KiCad also takes shapes that touch shapes already merged. **high**

**What differs.**
- `crates/ops/src/pad_edit.rs:193-215` (`recombine`) computes the pad's polygon once, before anything is merged: `let pad_polys = eda_drc::pad_shape::pad_polygons_in_footprint(...)`. It then makes a single pass over `fp.graphics` in index order, testing each graphic against that fixed polygon.
- KiCad's `pad.cpp::PAD::Recombine` rebuilds the pad's polygon on every call of `findNext`, and `findNext` runs again after each merge (`while( PCB_SHAPE* fpShape = findNext( layer ) )`). Each merged shape is added to the pad with `AddPrimitive( layer, primitive )`, which calls `SetDirty()`, so the next `TransformShapeToPolygon( padPoly, ... )` includes it:
  ```cpp
  auto findNext = [&]( PCB_LAYER_ID aLayer ) -> PCB_SHAPE*
  {
      SHAPE_POLY_SET padPoly;
      TransformShapeToPolygon( padPoly, aLayer, 0, maxError, ERROR_INSIDE );
      for( BOARD_ITEM* item : footprint->GraphicalItems() )
      { ...
          shape->TransformShapeToPolygon( drawPoly, aLayer, 0, maxError, ERROR_INSIDE );
          drawPoly.BooleanIntersection( padPoly );
          if( !drawPoly.IsEmpty() ) return shape;
  ...
  while( PCB_SHAPE* fpShape = findNext( layer ) ) { ... AddPrimitive( layer, primitive ); ... }
  ```
- So in KiCad, a chain of graphics grows the pad: segment A touches the anchor and segment B touches only A, and both are merged. In ours B is left out. It stays a loose `F.Cu` graphic of the footprint, outside the pad and its net.
- The restart also changes which shapes are found. KiCad's next scan starts again from the first graphic, so a graphic earlier in the list that touches a later merged one is taken too.

**How to see it.** Take a custom pad with a 0.5 mm circular anchor and two primitives: a segment (0,0)-(2,0) and a segment (2,0)-(2,2), both 0.2 mm wide. Run Edit Pad as Graphic Shapes (explode), then Finish Pad Edit (recombine).
- KiCad gives back both primitives.
- Ours keeps the first only. The second stays in `fp.graphics` on `F.Cu`.
- The same happens with no explode: draw the two segments next to a plain circular pad and recombine.

Test to add in `crates/ops/src/pad_edit_tests.rs`, named `recombining_follows_a_chain_of_shapes_that_touch_through_each_other`. Use `with_footprint(&m, vec![circle pad 500 um], vec![line("F.Cu",(0,0),(2000,0),200), line("F.Cu",(2000,0),(2000,2000),200)])`, explode/recombine, then assert `custom.primitives.len() == 2` and `fp.graphics.is_empty()`. Also add the variant with the two lines in reverse list order.

**Fix sketch.** Recompute `pad_polys` from the pad as it stands, primitives added so far included, and restart the scan after each merge, as `findNext` does.

**Unit-sensitive:** no.

### F2. Pads with no copper and no mask (paste-only, including paste-only custom pads) are dropped by the board reader and gone from the board we write. **high**

**What differs.**
- `crates/kicad/src/import.rs:1263-1268` (`parse_pad_geometry_in`) drops any pad whose `(layers ..)` names no copper layer: `notes.non_copper_pads_skipped += 1; return None;`.
- Only mask apertures are kept, through `mask_only_pad_graphics` at line 1819, which needs `F.Mask`/`B.Mask`. A pad on `F.Paste`/`B.Paste` alone is lost.
- KiCad's `pcb_io_kicad_sexpr_parser.cpp::parsePAD` keeps every pad, and the writer writes it back. Those pads are what the paste stencil is made of.

**How to see it.** `qa/data/pcbnew/stonehenge.kicad_pcb`: each of H1 to H4 has four `(pad "" smd custom ... (layers "B.Paste") (options ...) (primitives (gr_arc ...)))`.
- `eda import-kicad` then the studio writer: 176 pads against 192 in the original. All 16 paste pads are missing, and the import printed no note about them.
- `kicad-cli pcb export gerbers --layers B.Paste`: the original's `.gbp` has 101 flash/region records, the round trip's 85. The stencil openings of the four mounting holes are gone.

Test to add in the `crates/kicad` round-trip tests, named `a_paste_only_custom_pad_survives_import_and_export`. Input: a footprint with `(pad "" smd custom (at 1 1) (size 0.6 0.6) (layers "F.Paste") (options (clearance outline) (anchor circle)) (primitives (gr_poly (pts (xy 0 0) (xy 1 0) (xy 1 1)) (width 0) (fill yes))))`. Assert the written board contains that pad with its primitives.

The doc comment at `import.rs:87-104` gives the reason: phantom copper in the DRC. That only needs the pad kept out of the copper checks, not deleted.

**Unit-sensitive:** no.

### F3. An SVG's dashed or dotted stroke is imported as a solid line on the board. **medium**

**What differs.**
- `svg_import.rs:1708-1726` works out the dash style as `SVG_IMPORT_PLUGIN::Import` does, and the schematic side keeps it (`import_graphics_sch.rs::line_style`).
- On the board, `crates/ops/src/import_graphics.rs::board_items` drops `stroke.style`, because the IR's board `Shape` has no line style (`crates/model/src/ir.rs:1753`; the writer prints `(type solid)`).
- KiCad's `graphics_importer_pcbnew.cpp::MapStrokeParams` keeps it:
  ```cpp
  return STROKE_PARAMS( width, aStroke.GetPlotStyle(), aStroke.GetColor() );
  ```
- `PARITY-pcb.md` section 29 says that closed paths keep "the stroke's width and dash". That claim is wrong for the board.

**How to see it.** Import this file on Dwgs.User:
```xml
<svg xmlns="http://www.w3.org/2000/svg" width="100mm" height="100mm" viewBox="0 0 100 100">
<path d="M 10 10 L 90 10" stroke="#ff0000" stroke-width="1" stroke-dasharray="5 2" fill="none"/>
<rect x="10" y="20" width="30" height="20" stroke="#000" stroke-width="0.5" stroke-dasharray="1 1" fill="none"/>
</svg>
```
The written board has `(gr_line (start 10 10) (end 90 10) (stroke (width 1) (type solid)) ...)` and `(gr_poly ... (stroke (width 0.5) (type solid)) ...)`. KiCad writes `(type dash)` for both, because 5 ≥ 1.9 × 1 and 1 ≥ 1.9 × 0.5.

Test to add in the `crates/ops` import tests, named `an_svg_dash_array_is_the_board_shapes_line_style`.

The same gap affects any `.kicad_pcb` with dashed graphics that is read and written back. That is outside P8, but it has the same root (no stroke style on the board `Shape`).

**Unit-sensitive:** no.

### F4. Coordinates and widths of imported graphics and of custom-pad primitives are rounded to 1 µm, and "is this curve a line" is judged at 1 µm. **medium**

**What differs.**
- `graphics_import.rs:428-447`: `Mapper { iu_per_mm: 1000.0 }`, so `coord` rounds to µm and `line_width` truncates to µm.
- `spline_or_line` (`graphics_import.rs:533-573`) calls `approx_collinear` with KiCad's `SEG::ApproxCollinear( aSeg, 1 )` threshold of one unit. That unit is 1 µm here and 1 nm in KiCad (`graphics_importer.cpp::setupSplineOrLine`), so nearly flat curves become lines more often.
- The pad writer has the same rounding. The round trip of `test_starved_thermal` changes `(xy -0.48097 -0.570671)` to `(xy -0.481 -0.571)` in pad 1's `gr_poly`. In `issue5093`, J305's 16 custom pads lose their sub-µm vertices, and 94 pads' `(at -0.9625 0 90)` become `-0.963`.
- kicad-cli reads the result as a slightly different shape.

**How to see it.** Run `scripts/padcmp.py up/test_starved_thermal.orig.kicad_pcb up/test_starved_thermal.ours.kicad_pcb`. The only difference it reports is the rounding.

**Unit-sensitive:** yes. The µm → nm change fixes it if `Mapper::iu_per_mm` becomes 1e6 and `ARC_HIGH_DEF_UM` and the collinearity unit follow.

### F5. The DXF text's character width and vertical justification are not kept on the board. **medium (documented)**

**What differs.**
- `import_graphics.rs:173-195` writes a board `Text` with `size_um` = height for both sides, and moves the anchor by half a height to stand in for bottom or top justification.
- KiCad's `graphics_importer_pcbnew.cpp::AddText` sets `SetTextWidth( aWidth * ImportScalingFactor().x )` and `SetVertJustify( aVJustify )`. The width is `aWidth` = 0.9 × height × the style's width factor, from `DXF_IMPORT_PLUGIN::addText`: "The 0.9 factor gives a better height/width base ratio with our font".
- So the file we write has `(size h h)`, where KiCad writes `(size 0.9h h)` with `(justify ... bottom)`.
- This is listed in `PARITY-pcb.md` §29 "Approximations". It is kept here because it is a file difference.

**Unit-sensitive:** no.

### F8. Interactive placement grabs the picture by its bounding box's top-left corner. KiCad grabs it by the top-left item's position. **low**

**What differs.**
- `web/studio/src/kicad-port/importGraphics.ts:200-208` (`buildImportCmd` `build`) offsets the picture so that `bbox_um`'s (left, top) is at the cursor.
- `drawing_tool.cpp::PlaceImportedGraphics` uses `delta = cursorPos - preview.GetTopLeftItem()->GetPosition()`. `PCB_SELECTION::GetTopLeftItem` returns the item with the smallest `GetPosition().x`, then the smallest y. For a segment that is its start and for a circle its centre; with grouping on, the group is among the candidates.
- The final place is wherever the user clicks in both. Only the grab point while the picture is carried differs. Append Board already does this the KiCad way (`append_api.rs`, "the position of the top left item").

**Unit-sensitive:** no.

## Checked and found to match (no need to review again)

**DXF reader (`crates/kicad/src/dxf_import.rs` against `dxf_import_plugin.cpp` and dxflib):**
- Units:
  - `mapX`/`mapY`/`mapDim`, Y flip, `getCurrentUnitScale` (all 13 units and their factors).
  - `$INSUNITS` handling, including the reset to "default" (mm) for unknown values. This means the dialog's unit only applies when the file has no `$INSUNITS` at all.
- Line widths and layers:
  - `lineWeightToWidth` (BYLAYER → layer, ≥ 0 in 1/100 mm, else the default).
  - `addLayer` (BYLAYER becomes BYLWDEFAULT).
  - The placeholder layer 0 and `getImportLayer` fallback.
- Lines and polylines:
  - `addLine` (no OCS transform, as KiCad).
  - `addPolyline`/`addVertex`/`endEntity`, including KiCad's per-vertex width `startWidth / 100.0` quirk and the closing segment's width from the last record's attributes.
  - `insertArc` (bulge clamp ±2000, `MIN_BULGE` 0.0218, centre construction, the start and sign rules).
- Points and arcs:
  - `addPoint` (filled circle, radius `max(thickness, 0.01)`, line width 0.0001).
  - `addCircle`/`addArc` with OCS: `getArbitraryAxis` and `ocsToWcs` give the same matrix (row convention of `MATRIX3x3(VECTOR3,…)` checked), and the mirrored-OCS angle swap uses `GetScale()`, which reads m[0][0] and m[1][1].
- Ellipses:
  - `addEllipse`, both paths. With ratio 1 the arc start matches. Ours skips KiCad's double unit scaling, which is documented. Otherwise `TransformEllipseToBeziers` matches (`bezier_curves.cpp`: k = 4/3 tan(θ/4), quarter-turn split, the rotations).
- Text:
  - `addText` (the second-point swap rule, 0.9 width factor and style width factor, height/8 thickness, H/V justification mapping, the angle in degrees).
  - `addMText` (group 3 chunks then group 1, attachment point mapping).
  - `toNativeString`, compared line by line: `{}` and overbar levels, `^I ^J ^ `, `\P \X \~ \U+ \S \O \o`, the skipped codes, the escaped character, and the `%%c/d/p` replacements.
- Blocks and inserts:
  - `addInsert`'s matrix `(arbAxis * rot(-angle)) * scale` and translation `map(ins) - map(base)`, applied as `M·p + t`. This includes KiCad's own oddity of not subtracting the base before scaling, reproduced.
  - Insert row/column arrays are ignored in both.
  - An `IMPORTED_ARC` under a mirroring insert keeps its sweep sign in both, which is wrong in both and so parity.
- Splines: the "Invalid spline definition encountered" message, the < 2 control points refusal, degree elevation to 3.
- Unsupported entities: the messages for those KiCad reports.
- QA files read without messages:
  - `qa/data/pcbnew/large_coords_test.dxf` (1 line, 1 arc, 50 × 50 mm).
  - `common/import_gfx/examples/basic_ellipses.dxf` (a 128-vertex closed POLYLINE gives 128 lines).
  - `test_outlines.dxf` (121 circles, 94 lines, 28 arcs).
  - `issue22127_fusion360_splines.dxf` (78 curves, 6 lines).

**SVG reader (`svg_import.rs` against `svg_import_plugin.cpp` and nanosvg):**
- `Import`'s rules:
  - Hidden shapes and shapes with neither stroke nor fill are skipped.
  - Width −1 for no stroke.
  - `filled` = fill ≠ none and alpha > 0. A gradient counts as filled; the alpha of the paint union is a pointer in KiCad.
  - Black is treated as "unspecified" colour.
  - Dash classification (threshold 1.9 × width, dot/dash/dashdot/dashdotdot).
  - A filled open path is drawn twice: a closed polygon with no stroke, plus the open stroke.
- Paths and polygons: `DrawPath`/`DrawSplinePath`, `GatherInterpolatedCubicBezierPath` (threshold 0.001 × the box of the first three control points, the degenerate-chord fallback of 8303b2ad), `convertPolygon` and `PostprocessNestedPolygons` (the last shape's stroke and fill are used).

**Mapping and the board verb:**
- `MapCoordinate` (scale, then offset, then IU), `MapLineWidth` (≤ 0 means the default, the scale applies), `MapStrokeParams` (−1 becomes 0 on the board).
- `AddArc` (end and mid by rotation, radius ≥ INT_MAX/2 becomes a segment).
- `AddLine` skips zero length. `setupSplineOrLine` (but see F4 for the unit).
- `GRAPHICS_IMPORTER_BUFFER::ImportTo` size check and offset adjustment, with its message.
- The dialog: base defaults (scale 1.0, width 0.2 mm, group on, fix on, tolerance 1 mm, Layer checked), the units list order (Inches, Feet, Millimeters, Centimeter, Mils; std::map order), origin ÷ scale, the messages ("Please select a file to import.", "Please select a valid layer.", "There is no plugin to handle this file type.", "No graphic items found in file.", "Items in the imported file could not be handled properly.").
- The DXF unit preselection is Inches in KiCad and mm here. This is documented in `PARITY-pcb.md` §29; it is a deliberate default.
- Grouping applies when there are 2 or more board items, texts included.
- `ConnectBoardShapes` (`pcbnew/fix_board_shape.cpp`): `connectPair` for every pair of segment/arc/bezier, `findNext` (2-NN on the endpoints frozen at the start, ε², skip flags), the walk order and `beginFromEndPt`. Circles and polygons are left out of the tree; this is documented.

**Schematic importer (`import_graphics_sch.rs` against `graphics_importer_sch.cpp`):** `SCH_LINE` for lines and degenerate splines, the arc geometry and the max-radius rule, polygon fill mode by colour, `MapLineWidth` with abs. The no-stroke hairline and the text anchoring are documented differences. The dialog's units list and default selection are the same as the board's.

**Drops:**
- Board: `kicad_pcb`/`brd` go to Append Board, `dxf`/`svg` to Import Graphics.
- Schematic: `kicad_sch`, `png`/`jpg`/`jpeg`, `dxf`, `svg`.

**Custom pads:**
- The `(primitives ..)` reader against `parsePCB_SHAPE`'s legacy fill rule: a missing `fill` fills width-0 rects and circles, and every non-Edge.Cuts poly. Width ≤ 0 and unfilled becomes `DEFAULT_LINE_WIDTH` 0.1 mm. `gr_bbox`/`gr_vector` are proxies.

- Round trip and `kicad-cli pcb upgrade`: `custom_pads` (2 pads) and `issue19956` (5 pads) are identical. `test_starved_thermal` differs only by µm rounding (F4).

The per-primitive rules for segment, rect, circle (filled disc and/or 360° ring), polygon (filled area plus edge strokes when width > 0 or unfilled) and bezier match. Arcs are polylines here and `SHAPE_ARC` there, within max error.

Proxies are kept aside rather than turned into graphics; this is documented.
- `PAD::Recombine`: the non-custom conversion (circle and rect become their own anchor; other shapes become a polygon round a circle anchor of min(size)), hatch made solid, the move/rotate back, `findMatching` duplicates. See F1 for the chain growth.
- Pad Properties: a circle-anchor custom pad's size becomes (x, x) (`sizeOf`). The spoke angle follows circle ↔ non-circle (`onPadShapeSelection`). The "single polygon" check exists (message: F7).
