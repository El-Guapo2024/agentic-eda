## P13: zones

Read on main (`be562f2e`). KiCad is `8303b2ad` unless I say otherwise. I ran everything on scratch copies in `/tmp/findings-p13-p16.Ri3k`, using main's `target/debug/eda` and kicad-cli 10.99.0. I started one studio server on port 8820 and killed it afterwards.

### P13-1 (high). Fill All deletes every teardrop's fill, and the plots lose the teardrop copper. The lead in GAPS item 36 is confirmed, and the cause is wider than the uuids

**Fixed** on task-fix-bc-board-io: 14a1f007 (direction (a): `(legacy_teardrops yes)` while the design has teardrops, the uuid-less ones matched by layer and outline, KiCad's teardrop priorities for the studio's; slow test `refill_keeps_teardrop_fills`).

**What differs.** The studio's Fill All, its refill before DRC and before a plot, and the Zone Manager's refill all run `kicad-cli pcb drc --refill-zones --save-board` on a derived copy (`crates/kicad-engine/src/lib.rs:1030-1068`, `refill_zones`). In KiCad, the filler's entry point first throws away every teardrop zone and rebuilds teardrops only from the pads and vias whose own teardrop parameters are enabled:

`pcbnew/tools/zone_filler_tool.cpp::ZONE_FILLER_TOOL::FillAllZones`, which `pcbnew_jobs_handler.cpp::JobExportDrc` calls when `m_refillZones` is set:
```cpp
TEARDROP_MANAGER teardropMgr( board(), m_toolMgr );
...
teardropMgr.UpdateTeardrops( commit, nullptr, nullptr, true /* forceFullUpdate */ );
```
`pcbnew/teardrop/teardrop.cpp::TEARDROP_MANAGER::UpdateTeardrops`:
```cpp
if( m_board->LegacyTeardrops() )
    return;
...
// Old teardrops must be removed, to ensure a clean teardrop rebuild
if( aForceFullUpdate )
{
    for( ZONE* zone : m_board->Zones() )
    {
        if( zone->IsTeardropArea() )
            zone->SetFlags( STRUCT_DELETED );
    }
    m_board->BulkRemoveStaleTeardrops( aCommit );
}
...
TEARDROP_PARAMETERS& tdParams = pad->GetTeardropParams();
if( !tdParams.m_Enabled ) continue;          // the same for vias
```
`TEARDROP_PARAMETERS` defaults to `m_Enabled( false )`, and the parser does too (`parseTEARDROP_PARAMETERS`: `tdParams->m_Enabled = false;` until it meets `(enabled yes)`).

On our side, three things meet:
1. `crates/kicad/src/pcb.rs:76` always writes `(legacy_teardrops no)`. A board imported from a file older than 20230517 had `LegacyTeardrops()` true in KiCad (`pcb_io_kicad_sexpr_parser.cpp`: `if( zone->IsTeardropArea() && m_requiredVersion < 20230517 ) m_board->SetLegacyTeardrops( true );`), so KiCad kept its teardrops through a refill. Ours turns that off.
2. The studio's own teardrops (`Cmd::AddAllTeardrops`, `crates/ops/src/lib.rs:3951`, `eda_connectivity::generate_teardrops`) are plain zones with `(attr (teardrop (type padvia)))` (`crates/kicad/src/pcb_items.rs:105`). Nothing writes `(teardrops ... (enabled yes))` on the pads and vias behind them: the pad and via teardrop tokens are only the ones an imported file brought (`pcb.rs:1238`), and `RoutingSection::teardrop_settings` never reaches the derived board. So kicad-cli deletes those teardrops and builds none.
3. When kicad-cli does rebuild teardrops (pads with `(enabled yes)`), it writes them with no uuid at all. `pcb_io_kicad_sexpr.cpp::format( const ZONE* )` has `if( !aZone->IsTeardropArea() ) KICAD_FORMAT::FormatUuid( m_out, aZone->m_Uuid );`. As a result `entries_by_zone` (`crates/kicad/src/zone_fills.rs:267`, which matches by the uuid in `map`) can never match them to a design zone, and neither can `entries_of_imported_file` (`zone_fills.rs:280`, which skips a zone with an empty `Zone::uuid`).

The fill is then replaced wholesale (`KicadFills::take_from(None)`). Every teardrop becomes "no current fill". The derived `.kicad_pcb` writes them unfilled, so the Gerbers, the plots, the 3D render and live connectivity have no teardrop copper. The canvas still draws each teardrop solid from its outline (`PARITY-pcb.md` section 15, "a teardrop always draws as solid copper"), which hides the loss.

**How I saw it (run, not read).**
- `issue14549.kicad_pcb` (43 teardrops, version 20221018) imported with `eda import-kicad`: 43 of 43 teardrops had a fill after the import. After `eda board fill`: 0 of 43, and the cache held 1 zone. kicad-cli's saved `refill.kicad_pcb` had **0 teardrop zones** (it says `legacy_teardrops no`). kicad-cli refilling the original file kept all 43 (its file says `legacy_teardrops yes`).
- The same board, with Remove All Teardrops, `teardrop_settings.enabled = true` and Add All Teardrops through `/api/cmd`, gave 28 studio teardrops, then `POST /api/fill/kicad`: 0 of 28 filled, and 0 teardrop zones in the refilled board.
- `teardrop_issue_JPC2.kicad_pcb` (pads with `(teardrops ... (enabled yes))`): 5 of 5 filled after import. After the fill: 0 of 5, and the cache was empty. kicad-cli rebuilt 3 teardrops, all without a `(uuid ..)`.
- The rebuilt board from kicad-cli 10.99 (`refill.kicad_pcb` above, 3 teardrops, each with a `filled_polygon`) imported with `eda import-kicad`: the teardrops have `uuid: None`, and no `zone_fills.json` is written at all. So a board saved by current KiCad loses its teardrop fills at import, before any fill.
- The derived board after the fill: 43 teardrop zones, 0 with a `filled_polygon` (43 of 43 before). `kicad-cli pcb export gerbers`: F.Cu 117704 bytes before and 77003 after, B.Cu 73587 before and 61419 after. kicad-cli's DRC reports nothing either way.
- Side effects. `KicadFills::tally` counts the teardrops as fillable (`zone_fills.rs:166`, `fillable`), so the status bar's "N zones not filled (B)" never clears, `ZoneFillDirty` always has work to do, and `fill_api::ensure_filled` (the Plot dialog's "Check zone fills before plotting") starts kicad-cli again before every plot.

**Failing test.** `refill_keeps_teardrop_fills` in `crates/kicad-engine/tests/refill_zones.rs` (slow tier). Import `qa/data/pcbnew/issue14549.kicad_pcb`, run `refill_zones`, and assert that every `z.teardrop` zone has `fills.current(z).is_some()` with a nonzero area. A second case on `teardrop_issue_JPC2.kicad_pcb`. A fast test in `zone_fills.rs`: `scan_zone_fills` of a teardrop zone without `(uuid ..)` followed by `entries_of_imported_file` gives an entry.

**Fix directions (for the fixer to choose).** (a) Write `(legacy_teardrops yes)` while the design holds teardrop zones that kicad-cli should keep as they are, so `UpdateTeardrops` returns early and the zones are filled like any other zone. (b) Or make teardrops KiCad's: write the pads' and vias' `(teardrops ... (enabled yes))` from `teardrop_settings`, and match kicad-cli's rebuilt teardrops by layer, net and anchor position, since they have no uuid. Teardrops read from a file need a key other than the uuid either way. Note too that the studio's teardrops get priority 0 (`crates/connectivity/src/teardrop.rs:250`, `..Default::default()`), where KiCad gives them `MAGIC_TEARDROP_ZONE_ID` (30000) and up, per layer by decreasing area (`TEARDROP_MANAGER::setTeardropPriorities`). Under option (a) a GND pour of priority 0 would tie with them.

**Unit-sensitive:** no.

### P13-4 (medium). A new zone's net, priority and settings are not KiCad's

**What differs.** `pcbnew/tools/zone_create_helper.cpp::ZONE_CREATE_HELPER::createNewZone`:
- `zoneInfo.m_Netcode = highlightedNets.empty() ? -1 : *highlightedNets.begin();`, otherwise the net of the first selected connected item. The dialog shows `std::max( 0, m_Netcode )`, that is `<no net>` (`panel_zone_properties.cpp:137`). Ours: `ZoneDialog.tsx:185` `net || nets[0]`, the first net in alphabetical order. **Unit-sensitive:** no.

### P13-5 (medium). Adding a zone takes two undo steps

### P13-6 (medium). A double click on a selected zone's edge adds a corner instead of opening Zone Properties

**What differs.** `web/studio/src/components/canvas/Canvas.tsx:1455-1468`: a double click near an edge of the one selected zone inserts a corner at the snapped cursor point, which is not on the edge (`insertCorner(zone.outline, insertAt, sx, sy)`). ### P14-1. A board or footprint with an Extruded 3D Body loses it on import (high)

**Fixed** on task-fix-bc-board-io: 74f6e230 (kept as the file wrote it; the box is not ported).
- **What differs.** `crates/kicad/src/footprint_lib.rs:111-133` `models_from` keeps a `(model ...)` only when its second element is a text (`sexpr::txt(m, 1).filter(|p| !p.is_empty())?`). KiCad's typed model is `(model (type extruded) (hide no) (overall_height ..) (body_pcb_gap ..) (layer auto|pad_bbox|"F.Fab") (material plastic) (color ..|unspecified) (offset ..) (scale ..) (rotate ..))`. It is written by `pcb_io_kicad_sexpr.cpp::format( FOOTPRINT )` ("// Save extruded 3D body info.": `m_out->Print( "(model" ); m_out->Print( "(type extruded)" ); ...`) and read by `pcb_io_kicad_sexpr_parser.cpp::parseFOOTPRINT` (`case T_model: ... if( token == T_LEFT ) // Typed model (model (type extruded) ...)`). - **Unit-sensitive.** No. When the box is ported, `overall_height` and `body_pcb_gap` are `formatInternalUnits` (mm from nm).

### P14-2. A footprint flipped in the studio is written in a footprint frame KiCad never produces, and `flipped_frame` compensates for that in the model (high, root outside P14)
- **Fixed** on task-fix-a-kicad-names: fc8ee220 for a footprint made here (`pcb::half_turned`, test `a_flipped_footprint_is_written_in_kicads_frame`): written y-mirrored with the half turn in the orientation, its models as held; the Specctra session reader turns back. The reader and imported footprints are unchanged (a design.json already holding imported bottom footprints in the reader's frame would turn half a turn otherwise); a pad with an offset, deltas, chamfers, primitives or a padstack keeps its absolute angle (same copper, its own frame half a turn from KiCad's).
- **What differs.** The studio mirrors x for a bottom footprint and keeps the orientation as `-rot`:
  - `crates/kicad/src/pcb.rs:1126` and `:1286` write `px = -pad.at.0` for the pads, and `:1331` does the same for the courtyard;
  - `:975` writes the orientation as `-rot`;
  - `:1358` turns every model by `Model3d::flipped_frame` (`crates/model/src/footprint.rs:412`: offset (-x,-y,z), `rotate.z - 180`).

  KiCad's flip always mirrors y in the footprint's own frame and puts the half turn in the orientation. From `footprint.cpp::FOOTPRINT::Flip`: "When flipped around the X axis (Y coordinates changed) orientation is negated / When flipped around the Y axis (X coordinates changed) orientation is 180 - old orient. Because it is specific to a footprint, we flip around the X axis, and after rotate 180 deg", and `if( aFlipDirection == FLIP_DIRECTION::LEFT_RIGHT ) Rotate( aCentre, ANGLE_180 );`.

  The board geometry is the same. KiCad's operations that rebuild a footprint from its library are not:
  - `pcb_edit_frame.cpp::ExchangeFootprint` runs `aNew->Flip( aNew->GetPosition(), GetPcbNewSettings()->m_FlipDirection )` and then `aNew->SetOrientation( orientation )` with the old orientation. In KiCad, "Update Footprint from Library" or "Change Footprint" on a part the studio flipped therefore turns it half a turn, and its pads trade places.
  - With "Update 3D models" off, KiCad keeps the old models (`aNew->Models() = aExisting->Models()`). Their `rotate z 180` then puts the model half a turn off the new pads.
  - `drc_test_provider_library_parity.cpp::FootprintNeedsUpdate` flips a copy of the library footprint with `temp->Flip( { 0, 0 }, FLIP_DIRECTION::TOP_BOTTOM )` and `SetOrientation( GetOrientation() )`, so its pads differ from ours. A library-linked bottom part would then be reported as `lib_footprint_mismatch` when the library tables are present.

  An imported KiCad board is not affected: `q/` shows its bottom footprints written back in KiCad's own frame, with the same model numbers. Only footprints flipped by the studio are.
- **How to see it.** In `b/.kicad/ldo.kicad_pcb`, R1 (0603 on B.Cu) is `(at 10 10 0)` with `(pad "1" ... (at 0.825 0 0))` and `(rotate (xyz 0 0 180))`. KiCad's own flip of the same top footprint (pad 1 at -0.825) gives orientation 180, pad 1 at (-0.825, 0) and `(rotate (xyz 0 0 0))`.
  The test I would write is `a_flipped_footprint_is_written_in_kicads_frame` (`crates/kicad/src/pcb.rs` tests). It places R_0603 at rot 0 and flips it. It asserts that `(at x y 180)`, pad 1's local x is -0.825 and the model's rotation is (0 0 0), the same as `kicad-cli pcb upgrade` gives for a KiCad-flipped copy.
- **Fix direction.** Write a bottom footprint as KiCad's frame: local mirror_y, orientation `180 - (-rot)`. `flipped_frame` then goes away on the writer side, and the importer's half turn with it.
- **Unit-sensitive.** No.

### P14-3. The server refuses a scale or offset that KiCad's 3D Models tab accepts as typed (medium)
- **What differs.** `crates/model/src/fp_models.rs:139-155` `check_numbers` refuses any |offset| > 1000 mm and any |scale| outside [1e-4, 1e4]. It runs on every `set_board_models` (`crates/ops/src/fp_models.rs:65`, the dialog's OK) and on `add_board_model`.

  KiCad clamps only in the spin buttons and the wheel (`doIncrementScale`: `value = std::max( 1/MAX_SCALE, value ); value = std::min( value, MAX_SCALE );`, and the same in `doIncrementOffset`). A typed value goes through without a clamp (`updateOrientation`: `modelInfo->m_Scale.x = EDA_UNIT_UTILS::UI::DoubleValueFromString( unityScale, EDA_UNITS::UNSCALED, evaluateTextCtrl( xscale->GetValue() ) );`), and the parser reads any double.

  So in KiCad a scale of 0 (to flatten an axis) or a typed scale of 20000 is kept. In the studio it is refused with "the scale ... is out of range". Worse: a footprint read from a KiCad board that already holds such a model can never have its list edited. Any OK of the tab, even a Show toggle on another row, is refused, because the whole list is re-checked.
- **How to see it.** The test I would write is `a_list_with_a_typed_scale_kicad_keeps_is_accepted`. It calls `set_board_models` with one model of scale [0, 1, 1] and asserts Ok. It also imports a board whose model has `(offset (xyz 2000 0 0))`, toggles Show on it and asserts the edit is applied.
- **Unit-sensitive.** No.

### P14-4. The 3D viewer puts models on a fixed 1.6 mm board and leaves out the paste layer on the top side (medium)
- **What differs.** `web/studio/src/kicad-port/model3d.ts:130-133` `footprintZ` is `±(boardThicknessMm/2 + copperMm)`, and every caller passes `DEFAULT_STACK` (1.6, 0.035): `components/viewer3d/partModels.ts:75` and `components/footprint/ModelPreview3D.tsx:114`. The slab is a constant too (`components/viewer3d/scene.ts:81` `BOARD_THICKNESS_MM = 1.6`). KiCad differs in two ways:

### F16-4. A new text box's margins come from the layer's defaults; KiCad's are always 1.0025 mm (medium)

**What differs.** KiCad computes the margins once, in the constructor: `PCB_TEXTBOX::PCB_TEXTBOX` does `int defaultMargin = GetLegacyTextMargin(); m_marginLeft = defaultMargin; ...`. At that point the stroke is `PCB_SHAPE`'s `EDA_SHAPE( aShapeType, pcbIUScale.mmToIU( DEFAULT_LINE_WIDTH ), ..)` (0.10 mm, `board_design_settings.h:45`) and the text size is `EDA_TEXT`'s `DEFAULT_SIZE_TEXT` (50 mils). `GetLegacyTextMargin` is `KiROUND( GetStroke().GetWidth() / 2.0 ) + KiROUND( GetTextSize().y * 0.75 )` = 50 000 + 952 500 nm = 1.0025 mm. `DRAWING_TOOL::DrawRectangle` / `drawShape` then apply `SetStroke( m_stroke )` and `SetAttributes( m_textAttrs )`, which do not touch the margins, and `DIALOG_TEXTBOX_PROPERTIES` has no margin fields. So every new box gets 1.0025 mm on all four sides. KiCad's own `api_kitchen_sink.kicad_pcb` shows exactly that: `(margins 1.0025 1.0025 1.0025 1.0025)`.

Ours, `web/studio/src/kicad-port/pcbTextBox.ts:381` `newTextBox`, uses `legacyMarginUm(lineThicknessUm(defaults, layer), style.heightUm)`. On F.SilkS (0.1 mm line, 1 mm text) that is 50 + 750 = 0.8 mm.

**How to see it.** Draw a text box on F.SilkS. The studio writes `(margins 0.8 0.8 0.8 0.8)`; KiCad would write `1.0025`.
Test: `pcbTextBox.test.ts`, "a new text box has KiCad's constructor margins". Assert: `newTextBox(board, "F.SilkS", ..).margins` equals four times `legacyMarginUm(100, 1270)` (1003 µm today, 1002500 nm after the unit change), whatever the layer's defaults are.

**Severity.** Medium (wrong default; the text sits 0.2 mm further out and wraps wider).
**Unit-sensitive.** Partly. The default is wrong in any unit. 1.0025 mm is also not a whole micrometre, so even the fixed default rounds to 1.003 until the IR is in nanometres. That is the same rounding as F16-5.
