### P11-2 (medium). The Footprint Checker never reports two overlapping holes ("hole_to_hole"); KiCad's checker does
- **What differs.**
  - `crates/kicad-engine/src/footprint_check.rs:192` gives the scratch board `"rules": { "min_hole_to_hole": 0.0001 }` (0.1 µm), so that only overlapping holes are found.
  - kicad-cli's `drc_test_provider_hole_to_hole.cpp::testHoleAgainstHole` subtracts the DRC epsilon (`ADVANCED_CFG::m_DRCEpsilon = 0.0005`, 0.5 µm) and clamps `actual` at 0:
    ```
    actual = std::max( 0, actual - aHole->GetRadius() - otherHole->GetRadius() );
    ...
    int  minClearance = std::max( 0, constraint.GetValue().Min() - epsilon );
    if( ... && minClearance >= 0 && actual < minClearance )
    ```
    With a 0.1 µm minimum, `minClearance` is 0, so `actual < 0` is never true. The scratch board can only ever report `holes_co_located`.
  - KiCad's Footprint Checker does not use that provider. It calls `FOOTPRINT::CheckShortingPads`, in `dialog_footprint_checker.cpp::runChecks`:
    ```
    if( pad->HasDrilledHole() && other->HasDrilledHole() )
    { ...
        if( pad->GetPosition() == other->GetPosition() )
            aErrorHandler( pad, other, DRCE_DRILLED_HOLES_COLOCATED, pos );
        else
        {   std::shared_ptr<SHAPE_SEGMENT> holeA = pad->GetEffectiveHoleShape();
            std::shared_ptr<SHAPE_SEGMENT> holeB = other->GetEffectiveHoleShape();
            if( holeA->Collide( holeB->GetSeg(), 0 ) )
                aErrorHandler( pad, other, DRCE_DRILLED_HOLES_TOO_CLOSE, pos );
    ```
    This holds whatever the pads' numbers are, the same number included. It fires when hole A reaches hole B's centre line.
  - The `CHECKS` table (`footprint_check.rs:34`) lists `hole_to_hole` and the doc (`PARITY-fpedit.md` section 12) says "two drilled holes ... overlapping (`holes_co_located`, `hole_to_hole` ...)". The test at `footprint_check.rs:529-535` only checks the negative case (holes that do not overlap), so it cannot catch this.
- **How to see it (reproduced with kicad-cli 10.99).** `/tmp/findings-p11-p18.63AM/p11/h2h/t.kicad_pcb` is one footprint with two pads numbered 1, 1 mm drills 0.4 mm apart, and the checker's `min_hole_to_hole 0.0001` in `t.kicad_pro`.
  `kicad-cli pcb drc --severity-all` reports only `annular_width` and `lib_footprint_issues`, and no `hole_to_hole`. KiCad's checker would report "Drilled holes too close together" (the 0.4 mm distance is under the 0.5 mm radius).
  The test to write: `footprint_checker_reports_overlapping_holes`. Two THT pads, drill 1000 µm, 400 µm apart, `kinds(&c).contains("hole_to_hole")`.
  The fix: set a minimum above the epsilon, so the provider's clearance is positive, and keep only the violations whose holes collide. Or test the holes in Rust.
- **Unit-sensitive.** No. The value is mm in the project file.

  ```
  {
      selection.Remove( group );
      // Don't recurse; if we have a group of groups the user probably intends the inner groups to be saved
      group->RunOnChildren( [&]( EDA_ITEM* aItem ) { selection.Add( aItem ); }, RECURSE_MODE::NO_RECURSE );
  }
  ```
  `UpdateDesignBlockFromSelection` also does `copy->SetParentGroup( nullptr )`. The board half does strip the group (`board_selection_made`, `design_block_api.rs:388-390`); the schematic half does not.
- **Consequence.** Save to Linked Design Block (which runs Update from Selection on the one linked group) writes into the block's `.kicad_sch` a group linked to the block itself. The next Place Design Block with Place as group makes a linked group holding that inner linked group, so every save-then-place cycle nests one more level. In KiCad the block holds only the members.
- **How to see it.** Test `a_lone_schematic_group_saved_as_a_block_is_saved_without_the_group`: in `design_block_tests.rs` style, group three symbols into `G` (linked to `Power:Trio`), POST `/save` `{what:"selection", ids:[G], update:true, name:"Trio"}`, read the block's `.kicad_sch`, and assert that it has no `(group` and that its three symbols are there.
- **Unit-sensitive.** No.

### P18-3 (medium). Board Save Selection drops every selected group, not only a lone one
- **What differs.** In `design_block_api.rs:388-390`, `dr.groups.retain(|g| !picked.contains(g.id.as_str()))` removes every group the user picked, whatever else is picked. KiCad's `pcb_design_block_utils.cpp::SaveSelectionAsDesignBlock` and `UpdateDesignBlockFromSelection` strip only when `selection.Size() == 1`. In a larger selection, `saveSelectionToDesignBlock` keeps each group as a deep clone (`deepCopy = static_cast<PCB_GROUP*>( item )->DeepClone(); deepCopy->SetParentGroup( nullptr ); tempBoard->Add( deepCopy ...)`).
- **How to see it.** Select group `G` (two footprints) plus a lone track, then Save Selection as Design Block. KiCad's block file has `(group "G" ...)`; ours has none. The test to write: `a_group_in_a_larger_board_selection_stays_a_group_in_the_block`.
- **Unit-sensitive.** No.

### P18-4 (medium). The board placement renumbers references the board already uses, and puts a reference the board has unplaced onto that part; KiCad keeps the block's footprints as they are
- **Docs fixed** on task-fix-f-editing: 8a567378 (PARITY-pcb.md section 36's row says how the references differ); the behaviour is unchanged (a reference is an id here).
- **What differs.** `pcb_paste.rs:594-608` (`insert_copies_all`, the footprints) handles two cases:
  - With `reuse_unplaced: true` (set in `copies_from_clipboard:493`), a block footprint whose reference is an unplaced part of the board becomes a placement of *that* part. The part's own nets and footprint stay; the block's `pad_nets` are not used.
  - Otherwise the footprint gets a new part under `unique_reference(..)`.

  KiCad `AppendBoard` calls `placeBoardItems( commit, brd, false, false /* Don't reannotate dupes on Append Board */, aSkipMove )`, so each footprint of the block is a new footprint with the block's reference and the block's nets, duplicates included.
  `PARITY-pcb.md` section 36 marks the row "identical in effect" while it names the renumbering. The reuse of an unplaced part is not documented at all.
- **How to see it.** On a board where `R1` is in the netlist but not placed, place a block holding `R1` on net `X`. Ours: the board's `R1` is placed, on its own nets. KiCad: a second footprint `R1` on net `X`. The renumbering is the IR's (a reference is an id); at the least, change the row's status and document the unplaced-part reuse.
- **Unit-sensitive.** No.

### P18-5 (low). "Place as group" with one item: no group for a plain file on the schematic, and the board's ≥2 rule
- **What differs.** `design_blocks.rs:47-49` (`group_placed`) skips the group when `ids.len() < 2 && placement.block.is_empty()`. KiCad's `sch_drawing_tools.cpp::ImportSheet` (`placeSheetContents`) makes the group whenever `placeAsGroup` is set, with no count check (`group = new SCH_GROUP( screen ); ... commit.Add( group, screen )`). The ≥2 rule (`groupableCount >= 2`) is the board's `AppendBoard` only, and ours applies it there correctly.
  This affects Import Sheet of a one-item file with Place as group (and the group of a block is fine).
- **Unit-sensitive.** No.

### P18-6 (low). Save to Linked / Update from Selection on a lone group that is already linked runs a design command anyway
- **What differs.** `design_block_api.rs:455-475` (`Source::link`) always steps `LinkDesignBlock` for a selection. For a lone group that already has a link, `link_design_block` (`crates/model/src/groups.rs:395-402`) changes nothing, but `board::step` is still run, which may record an undo step that does nothing (not confirmed by running). KiCad commits only `if( !group->HasDesignBlockLink() )` ("Set Group Design Block Link").
- **How to see it.** Run Save to Linked on a linked group, then Undo once. Expected: the step before the save is undone, not a no-op.
- **Unit-sensitive.** No.

### P18-7 (low). Messages and their order
- `web/studio/src/actions/designBlockActions.ts:196`: with no library selected, an update always says "Please select a design block to save the schematic to.". On the board KiCad says "Please select a library to save the design block to." (`UpdateDesignBlockFromBoard`, and `UpdateDesignBlockFromSelection`'s `!aLibId.IsValid()`). `design_block_api.rs:479-481` (`prepare_with`) has the same issue.
- `designBlockActions.ts:195`: the empty selection is checked before the library. That is KiCad's schematic order. The board's `PCB_EDIT_FRAME::SaveSelectionAsDesignBlock` checks the library first ("Please select a library ...") and then the selection.
- `designBlockActions.ts:168`: the toast "Design block '%s' saved to library '%s'." is not KiCad's (KiCad says nothing: `RefreshLibs(); SelectLibId(..)`).
- `crates/kicad/src/design_block.rs:120` / `designBlocks.ts:113` (`clean_fields`): `name.trim()` strips both ends. KiCad's `TransferDataFromGrid` uses `wxString::Strip()`, which by default strips trailing whitespace only. A field name " A" stays " A" in KiCad.
- `design_block_api.rs:346-348`: the refusal "The board has nothing in it to save as a design block." is invented (already documented in `PARITY-pcb.md` section 36).
- **Unit-sensitive.** No.

### P18-8 (low). The metadata reader takes `"description": null`
- `design_block.rs:158-163` (`Metadata` with `Option<String>`) reads `null` as empty. KiCad's `DesignBlockLoad` does `contains("description")` and then `get<std::string>()`, which throws on null, so the block is "Design block metadata file '%s' could not be read." and is left out of the tree. KiCad never writes null, so this is cosmetic.
- **Unit-sensitive.** No.

## P18: checked and matching (no need to review again)
- **`.kicad_blocks` layout.** Library folder `<lib>.kicad_blocks`, block folder `<name>.kicad_block`, files `<name>.kicad_sch` / `.kicad_pcb` / `.json` (`DesignBlockLoad`, `DesignBlockSave`). Either design file may be absent, and so may the metadata file.
- **Metadata writer** (`metadata_text`) = `nlohmann::ordered_json` `dump(0)`: key order description, keywords, fields; empty fields `{}`; the string escapes (`\b \f \n \r \t`, other control characters as `\u00xx` in lower case, UTF-8 raw). **Reader:** fields kept in file order, and a repeated key keeps its first place with the later value (`ordered_map::operator[]`). A non-string value is "could not be read".
- **`DesignBlockSave`:** refusal order and messages word for word ("Design block does not have a valid library ID.", "... schematic or board file.", "Schematic source file '%s' does not exist.", "Board source file ...", "Design block folder '%s' could not be created.", "... could not be saved as design block at '%s'.", "Design block metadata file '%s' could not be saved."). A source file that is already the destination is not copied, and the metadata is written atomically.
- **`DesignBlockDelete`, `CreateLibrary` and `DeleteLibrary`:** messages. Our `DeleteLibrary` deliberately accepts `.kicad_block` sub-folders, where KiCad's check would refuse any non-empty library (documented in `design_block.rs`).
- **`DesignBlockEnumerate`:** names before the first dot, a documented deviation. Ours lists the whole name and refuses a '.' in a new name.
- **Search terms** (`DESIGN_BLOCK::GetSearchTerms`, weights 4/8/16/4/1/1); history of 7 (`while size() >= 8 pop_back`); the four check boxes' defaults (repeated off, sheet off, group on, keep annotations off: `app_settings.cpp`).
- **Context menu** (`DESIGN_BLOCK_CONTROL::AddContextMenuItems` and `SCH_`/`PCB_DESIGN_BLOCK_CONTROL::Init`): entries, conditions, priorities, and the action labels word for word.
- **Name check** (`TransferDataFromWindow`: `FindIllegalLibraryNameChar` plus `/`, "Illegal character '%c' in name '%s'."); "Duplicate fields are not allowed."; the double-space and newline cleanup of field names.
- **Properties:** a rename saves under the new name, then deletes the old one, asking first with `checkOverwrite` ("Design block '%s' already exists in library '%s'." / "Overwrite existing design block?" / "Overwrite"). The read-only refusal is "Library '%s' is read only.".
- **Delete:** "Delete design block '%s' in library '%s' from disk?" and "Design block '%s' deleted from library '%s'".
- **Save and Update flows:** the dialog only for new blocks and for Update from Sheet (name locked); `checkOverwriteDbSchematic` / `checkOverwriteDbLayout` text; "Design blocks with nested sheets are not supported."; a lone selected sheet is the sheet's save.
- **Default name:** a lone named group gives its name, otherwise the screen's or board's file stem.
- **After saving a selection:** a new group named after the block and linked, its members leaving their old groups. A lone group takes the link only if it has none.
- **Place Design Block:** schematic: "Design block has no schematic to place."; board: "Design block has no layout to place."; "Could not find design block %s.".
  - The schematic group's name gets the suffix 1, 2, ... only with repeated copies. A sheet placed from a block is named after the block, its file is the block's stem, and its group is named after the block without a suffix.
  - On the board: a group only when there are ≥ 2 top items; named after the block, with no suffix; the repeat loop.
  - Place Linked: the board's has no repeat loop; the schematic's goes through `placeDesignBlock` (repeat honoured). The messages "Design block %s does not have a board file." / "... schematic file.".
- **Group `(lib_id "Lib:Name")`:** written after `locked` and before `members` in the `.kicad_pcb`; a linked group of one member is kept.
- **Out of scope here** (Import Sheet, P4/P8): annotation when a block is placed with Keep annotations off or on. KiCad keeps duplicates, or clears to `?` when auto-annotate is off, and always annotates power symbols; ours numbers anew (an IR constraint).
