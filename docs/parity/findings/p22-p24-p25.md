## F1. A zone with a hole becomes two zones: the hole is written as a filled zone of its own (high)

**Fixed** on task-fix-bc-board-io: 53558ea4 (`Zone::holes`; the cutout and merge keep holes too).

**What differs.** `crates/kicad/src/import.rs:2388-2403` (`import_zones`): `let outlines = sexpr::find_all(z, "polygon")...; for outline in &outlines { out.push(Zone { outline: outline.clone(), ..zone.clone() }) }`. The doc comment at `import.rs:2219-2221` even says "the first is the outline, the others its holes" and still makes one `Zone` per `(polygon ...)`. KiCad: `pcb_io_kicad_sexpr_parser.cpp::parseZONE`, `case T_polygon`:

```cpp
// Remark: The first polygon is the main outline.
// Others are holes inside the main outline.
zone->AddPolygon( outline );
```
and `zone.cpp::ZONE::AddPolygon`: `if( m_Poly->OutlineCount() == 0 ) m_Poly->AddOutline( aPolygon ); else m_Poly->AddHole( aPolygon );`

So a keepout ring (Eagle's restrict ring around a mounting hole, which the Eagle importer writes as a footprint rule area with a hole) comes back as a keepout over the whole disc, and a copper pour with a cut-out is poured over the cut-out. The second zone gets a fresh UUID on export.

**How to see it.** `test_eagle.brd` -> kicad-cli: footprints AFIT1 and AFIT2 each have one keepout zone with two `(polygon)` blocks (outline + hole). Our export has two keepout zones per footprint (Adafruit AHT20: 8 footprint zones become 16). kicad-cli DRC on our export reports 2 `items_not_allowed` ("Items not allowed (keepout area of AFIT1)", Pad P$1 of AFIT1) that kicad-cli's own board does not have.
Test: `zone_with_a_hole_is_one_zone_with_a_hole`: input a board with `(zone (net 0) (layer "F.Cu") (keepout (tracks not_allowed) ...) (polygon (pts <10x10 square>)) (polygon (pts <2x2 square in the middle>)))`; assert `routing.zones.len() == 1` and that a point in the middle is not inside the zone; and that the re-exported file has one `(zone` with two `(polygon`.

**Severity.** High (wrong geometry; DRC and the zone filler see copper/keepout where the file has a hole; file KiCad reads differently). Applies to every board read, not only foreign ones. Needs a hole list on `ir::Zone` (or a polygon-with-holes outline).
**Unit-sensitive.** No.

**Severity.** High (wrong connectivity; file KiCad reads differently). Overlaps P25 (padstacks); the B.Cu entry of such a padstack also loses its `thermal_bridge_angle` and `zone_connect` (J13).

## P25-1 (high). Finish Pad Edit misses graphics that touch the pad only through another merged graphic

**What differs.** `PAD::Recombine` (`pcbnew/pad.cpp::PAD::Recombine`) rebuilds the pad's polygon on every pass of `findNext`. Each merged shape is added to the pad first (`AddPrimitive` then `SetDirty()`), so a later shape that touches only an earlier merged shape is merged too. The merge is transitive.
```cpp
auto findNext = [&]( PCB_LAYER_ID aLayer ) -> PCB_SHAPE* {
    SHAPE_POLY_SET padPoly;
    TransformShapeToPolygon( padPoly, aLayer, 0, maxError, ERROR_INSIDE );   // the pad as it is *now*
    ...
while( PCB_SHAPE* fpShape = findNext( layer ) ) {
    ...
    AddPrimitive( layer, primitive );                                        // the pad grows
```
Our version computes the pad polygon once, from the pad as it was before any merge (`crates/ops/src/pad_edit.rs:193`, `let pad_polys = ...pad_polygons_in_footprint(&fp.pads[index]...)`). It then makes one pass over the graphics (`pad_edit.rs:203-216`). A graphic that does not overlap the anchor itself is never merged.

**How to see it (confirmed with the binary).**
1. Make a custom pad: a circle anchor 0.8 mm across at (0,0), with primitive 1 a 0.2 mm segment (0,0)-(1,0) and primitive 2 a segment (1,0)-(1,3). This is an L-shaped pad.
2. Run `explode_pad`, then `recombine_pad` straight away, with no edit in between.
3. Result: the pad has one primitive left, and `graphics` holds `{segment F.Cu (1000,0)-(1000,3000) w=200}` as a loose copper drawing of the footprint.
4. KiCad gives the pad back with both primitives and no loose graphic.

Any custom pad with chained primitives (L-shaped thermal pads, finger pads built from segments) loses copper this way after an explode and recombine. The loose F.Cu graphic is then written into the `.kicad_mod`.

Test to write, in `pad_edit_tests.rs`: `recombining_merges_shapes_that_touch_the_pad_only_through_another_merged_shape`. Input: the pad above. Steps: explode, recombine. Assert `custom.primitives.len() == 2 && f.graphics.is_empty()`.

**Fix direction.** Loop until no new graphic is found, and rebuild `pad_polys` after each merge (or union the merged shape's polygon into it).

**Unit-sensitive.** No. `MAX_ERROR_UM = 5` (`pad_edit.rs:28`) has to become 5000 in the nm change.

## P25-2 (high). Pins common to all units (unit 0) are kept only in unit A, so each footprint's gate list is wrong

Test to write: in `crates/kicad/src/symbol_lib.rs` tests, `a_common_pin_of_a_multi_unit_symbol_is_in_every_unit`. Load the installed Device library's `D_Dual_CommonAnode_AKK_Split`. **Unit-sensitive.** No.

## P25-3 (medium). Recombine's duplicate removal (`findMatching`) only looks at the edit layer and needs exact equality

**What differs.** In `PAD::Recombine`, `findMatching` checks every pad layer, and its comparison ignores the layer:
```cpp
if( GetLayerSet().test( other->GetLayer() ) && aShape->Compare( other ) == 0 )
    matching.push_back( other );
```
`EDA_SHAPE::Compare` (`common/eda_shape.cpp`) compares start/end, the shape, arc mid, bezier and polygon vertices with `EPSILON 2` (IU), plus the stroke width (also ±2), line style and fill. It does not compare the layer. So a copy of a merged shape on `F.Mask` or `F.Paste` (common in vendor footprints, which the comment there mentions) is deleted with it.

Ours (`pad_edit.rs:210-215`) only matches graphics with `layer() == layer` (the copper edit layer). `same_shape` (`pad_edit.rs:115-121`) also compares the layer and needs exact equality.

**How to see it.** Take a footprint with a custom pad on F.Cu/F.Paste/F.Mask, plus a free F.Cu polygon and an identical F.Mask polygon touching the pad. Recombine.
- KiCad: both polygons leave the footprint and one primitive is added.
- Ours: the F.Mask copy is kept.

Test to write: `recombining_deletes_identical_copies_on_the_pads_other_layers`.

**Unit-sensitive.** Partly. KiCad's ±2 IU tolerance is ±2 nm. Today exact equality in µm is looser than that. After the nm change, exact equality is slightly stricter than KiCad, so port the epsilon then.

## P25-4 (medium). Swap Pad Nets moves a pin, not a pad: pads that share a number cannot get different nets

**What differs.** In KiCad each `PAD` has its own net code. `SwapPadNets` calls `pads[i]->SetNetCode( newNetForIndex( i ) )` and touches only that pad. Other pads with the same number change only if copper connects them, and then only as the user chooses in `PromptConnectedPadDecision`.

Here a pad's net is its pin `REF.NUM` in `design.nets` (`pad_nets.rs:41-43`, `net_of`, and `move_nets` at lines 249-259, which retain and insert the pin). Selecting `U1.9#1` (one of five thermal-pad pieces numbered 9) moves the pin `U1.9`, and with it all five pieces.
- With "Ignore Unselected Pads", KiCad leaves `U1.9#2..#5` on GND. We move them anyway.
- Selecting two pads with the same number (`U1.9#1` and `U1.9#2`) and another pad gives two moves of the same pin. The last one wins.

**How to see it.** Take a QFN footprint whose exposed pad is several pads all numbered "9" on GND. Swap Pad Nets on `U1.9#1` and `U1.3`, and answer "Ignore Unselected Pads".
- KiCad: only that one copper piece changes net. DRC then reports shorts against its siblings.
- Ours: all of pad 9 changes.

Test to write: `swapping_one_of_several_pads_with_the_same_number_moves_only_that_pad`. Expected to fail by design today. Either the IR gets per-pad nets, or the verb should refuse an `nth > 1` pad or a number that several pads share, with a message.

**Unit-sensitive.** No.

## P25-5 (medium). Pad Properties, Front/Inner/Back to Custom: inner layers after In1 get the inner shape, where KiCad gives them the front's

**What differs.** `DIALOG_PAD_PROPERTIES::transferDataToPad`'s `setMode` only sets up layers that the *new* mode's `ForEachUniqueLayer` lists:
```cpp
aPad->Padstack().SetMode( mode );
aPad->Padstack().ForEachUniqueLayer( [&]( PCB_LAYER_ID layer ) {
    if( !oldStack.HasExplicitDefinitionForLayer( layer ) ) { ... newLayerMap[layer] = ...; } } );
```
For CUSTOM, `ForEachUniqueLayer` walks the existing `m_copperProps` keys only. After Front/Inner/Back those keys are `F_Cu`, `INNER_LAYERS` (= `In1_Cu`, `padstack.h:180`) and `B_Cu`. No entry is created for In2..In(n-2). Reading those layers goes through `PADSTACK::CopperLayer( aLayer ) const`, which falls back to `m_copperProps.at( ALL_LAYERS )`, and `ALL_LAYERS` is `F_Cu`. On a 4-layer board KiCad therefore shows, and then writes, `In2.Cu` with the **front** shape, while `In1.Cu` keeps the inner shape.

Ours (`web/studio/src/kicad-port/padStack.ts:156-162`, `changeMode`) gives every inner layer the inner shape: `copy(known ?? (isInner(name) && inner ? inner : front))`.

**How to see it.** Take a 4-layer board and a PTH pad set to Front/Inner/Back (front oval 3x1.5, inner circle 1.27, back oval 2.5x1). Switch to Custom, choose edit layer In2.Cu, press OK.
- KiCad: the file has `(layer "In2.Cu" (shape oval) (size 3 1.5))`.
- Ours: `(shape circle) (size 1.27 1.27)`.

Test to write (`padStack.test.ts`): `changeMode from front_inner_back to custom leaves In2..In(n-2) on the front's shape`.

**Unit-sensitive.** No.

## P25-6 (low). Unit pins are ordered by the file's y, not KiCad's flipped internal y

**What differs.** `GetUnitPinInfo` sorts by `SCH_PIN::GetPosition()`, x first and then y. These are internal coordinates with y pointing down: the parser reads pin positions with `parseXY( true )` (`sch_io_kicad_sexpr_parser.cpp::parseSymbolPin`, `case T_at`), which flips y.

`unit_pin_info` (`fp_units.rs:81`) sorts the raw file y (y up, `symbol_lib.rs:375`). Pins that share an x therefore come out in reverse order. For a 74xx gate: KiCad gives `[1, 2, 3]` and we give `[2, 1, 3]`. The test `fp_units.rs:166` asserts our order, and PARITY section 45 quotes "2/1/3 against 5/4/6".

Swap results are the same while the units are copies of each other, since both units flip the same way. The `(units ..)` we write (`pcb.rs:1050`) differs from KiCad's in pin order, and the pairing differs for units whose pins are not laid out alike.

**Fix.** Sort by `(x, -y)`. **Unit-sensitive.** No.

## P25-7 (low). `(units ..)` is written only for footprints of symbols with two or more units

`NETLIST_EXPORTER_XML` (`netlist_exporter_xml.cpp`, around line 616) gives a unit list to every symbol with a library symbol, one-unit symbols included (`GetUnitPinInfo` gives at least one unit). After Update PCB from Schematic, KiCad's board has `(units (unit (name "A") (pins ...)))` on every footprint.

`pcb.rs:1042-1047` writes the derived list only when `derived.len() >= 2`. KiCad reads the result the same way for gate swapping (it needs two units), so only the file text differs.

**Unit-sensitive.** No.

## P25-8 (low). A PTH pad that keeps all layers does not write `(remove_unused_layers no)`

`format( const PAD* )` (`pcb_io_kicad_sexpr.cpp`, around line 1828) writes `KICAD_FORMAT::FormatBool( m_out, "remove_unused_layers", aPad->GetRemoveUnconnected() )` for every `PAD_ATTRIB::PTH` pad. That is `(remove_unused_layers no)` when the pad keeps all its layers. When the flag is set and the pad is on a board, it also writes `(zone_layer_connections ...)`.

`padstack_io.rs:138-146` (`unconnected_text`) writes nothing for `KeepAll`, and the doc says so. KiCad reads both forms the same way. This only makes the file differ from what KiCad writes. **Unit-sensitive.** No.

## Known limits confirmed (already in PARITY; no new finding)

- **Swap Pad/Gate Nets and zones.** KiCad's `GetConnectedItems( pad, 0 )` passes no `EXCLUDE_ZONES` flag. So `SearchClusters( CSM_CONNECTIVITY_CHECK, false, net )` walks *through* filled zones (`connectivity_algo.cpp::SearchClusters`). Tracks, vias and pads joined to the pad only by a pour are swapped too, or listed as unselected pads; only the zones themselves are skipped (`default: continue`). Our `pad_clusters` builds the graph with `ZoneCopper::default()` (`pad_cluster.rs:28`). This is documented ("the pads that only a zone fill joins"). It matters most when a GND pad is swapped on a board with a GND pour: KiCad would offer to move every GND pad that touches the pour.
- **Explode and proxies.** KiCad turns proxy items (the number box and the spoke template) into footprint graphics. We hold them in `PadEditMode::proxies`. This is documented.
- **Explode and padstacks.** KiCad explodes only the front, or `ALL_LAYERS`, layer's primitives ("TODO(JE) padstacks"). We do the same through the pad's own fields.
